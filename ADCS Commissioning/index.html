      If it didn't

      +Every overpass

      Manual sections 2 and 16, pages 8–11 and 59

      Three things at every pass, however far through commissioning you are. Nominal ADCS operation needs very few telecommands (set estimation and control mode, set enabled state), but commissioning adds many more.

      Synchronise time

      Send a single Set Unix Time command. Position prediction and the magnetic field model both depend on it.

      Check ADCS health

      Read the error flags in the ADCS State telemetry and the current and temperature frames. Persistent flags need attention, and so do telemetry values that wander far from nominal.

      Check for new TLEs

      Upload fresh two-line elements whenever new ones are published. Roughly once a day is enough, not every pass.

      Logging so that frames line up

      The ADCS can log to two SD files (LOG1 and LOG2) so every channel in a record comes from the same processing iteration. If you sample over the bus from the OBC instead, request frames between iterations: read the ACP Execution State frame and wait until Time Since Iteration Start reaches 500 ms (an iteration never takes longer), then pull everything you need. A frame requested just before an iteration ends can come from the previous one.

      Error flags come in two kinds. Status flags track the current state every iteration. Latching error flags stay set until you clear them by command, so an error that came and went between two reads still shows up. If it is still set on the next read, it's persistent.

      +Built-in safeguards

      Manual section 17, pages 60–62

      Several recoveries run automatically, so a failing module doesn't take the satellite with it. Try the first one.

      I²C and unresponsive modules

      Every second the ADCS checks the CommsError and run-time flags of CubeControl Signal and Motor, CubeSense, CubeWheel and CubeStar. Three consecutive run-time errors, or more than 10 accumulated communication errors (30 on ACP v3), power-cycle the module. After 5 power cycles it is switched off for good. Ten seconds of clean communication (60 s on ACP v3) resets the error counter, so only persistent faults get handled.

      Estimator divergence

      If the absolute values of the three estimated rate components add up to more than 1000 deg/s, the estimator goes to none (mode 0). Any controller that needs it goes to none too, except B-dot, which needs no estimator.

      Wheel errors ACP v5 and up

      A wheel that doesn't track its momentum command raises a flag. That wheel's control, and magnetic momentum dumping, are paused, so the torquers can't spin the satellite up chasing an unresponsive wheel. If it recovers, control resumes. After 5 failed power cycles, and with wheelErrorHandling true, control falls back to Y-Thomson (mode 2) to detumble.

      Faulty magnetometer ACP v5 and up

      If any axis stays constant for 10 s a run-time error is raised and the module power-cycles every 10 s. After 3 cycles, with autoRecoverMtm true, the mode steps along: main via Signal (0), redundant via Signal (1), main via Motor (2), none (3). Via Motor there is no temperature compensation and raw readings are 12-bit rather than 16-bit.

      Faulty MEMS rate sensors ACP v5 and up

      With rateSensorErrorHandling true, an axis that stays constant or zero for 30 s moves estimation off the gyros. From MEMS rate sensing with a faulty Y sensor in Y-Thomson: magnetometer rate filter (2) and B-dot (1). From Gyro EKF with any faulty sensor and control above B-dot: Full-state EKF (5) and control none (0). A reading beyond 80 × RateSensorMult deg/s sets the out-of-range flag.
